# ADR 0001：头像池交付方式

日期：2026-07-30
状态：Proposed — 需要产品/运维确认后才能执行迁移。

## 背景

应用使用 `poolAvatarUrl(userId)` 将缺少自定义头像的用户稳定映射到
`/avatars/pool/{0..19999}.svg`。当前池包含 20,000 个文件、约 28.6 MB，占
`public/` 文件数的 97.8% 以上。每次构建都会检查池，standalone/Docker 制品也会
携带这些文件。

这些 URL 会进入浏览器/CDN 缓存，也可能被搜索引擎或外部页面引用。未经迁移
设计直接缩池会让同一用户的 fallback 头像改变；直接换域名会让旧缓存和历史
引用失效。

## 选项

### A. 缩小本地池

- 优点：最简单，减少文件数和制品体积。
- 风险：`hash % POOL_SIZE` 改变后，绝大多数用户的头像槽位会变化；需要保留
  旧 URL 或接受视觉身份变化。
- 回滚：恢复 20,000 池和旧映射。

### B. 发布到 R2/CDN，并保持路径兼容（推荐）

- 将现有 20,000 个文件按内容原样发布；
- 优先在边缘把 `/avatars/pool/*` 映射到对象存储，保持公开 URL 不变；
- 如果基础设施不能保留路径，则应用先双读：新 CDN URL 失败时回退旧本地路径；
- 至少观察缓存命中、404、跨域和 fallback 后，再从 runner 制品删除本地池。

优点：用户映射和公开 URL 可保持稳定，应用制品减少约 28.6 MB/20,000 文件。
风险：增加 R2/边缘路由依赖，需要缓存和回源监控。

### C. 保留本地池，但从应用镜像解耦

- 将头像池做成独立只读 volume/静态制品，在部署时挂载；
- 应用 URL 不变，但部署系统需要原子更新两个制品。

优点：不依赖外部 CDN。风险：增加部署耦合和回滚复杂度，不符合当前单一不可变
runner 的方向。

## 建议决策

选择 B，但必须先确认生产边缘是否能保持 `/avatars/pool/*` 路径，以及 R2
bucket/cache policy。未确认前保持 `POOL_SIZE=20000` 和现有 URL；本阶段只修复
构建完整性检查，不上传对象、不修改 URL。

## 验收

- 对全部 20,000 个对象核对 size/hash；
- 旧路径与新对象内容一致，抽样响应 `Content-Type=image/svg+xml`；
- 观察 7 天 404、回源率和缓存命中；
- 自定义头像、数据库已有 `/avatars/*`、pool fallback 均正常；
- runner 删除本地池前完成双读/回滚演练。

## 回滚

保留原始 pool manifest 和 runner 版本；边缘路由可立即切回应用静态文件。不得在
确认旧路径已恢复前删除 R2 对象或改变 `POOL_SIZE`。
